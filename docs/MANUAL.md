## 一、登录与身份

### 登录

打开系统地址，用分发的账号密码登录。默认演示账号是 `owner` / `demo1234`（**上线后必须改**）。

登录成功后凭证存在浏览器本地，有效期 **12 小时**，过期需重新登录。

### 你的角色决定你能看到什么

系统有四种角色，能力与可见范围是**分开控制**的：

| 角色 | 能做什么 | 看不到什么 |
|---|---|---|
| **OWNER** 店主 | 全部功能，含加人改角色 | — |
| **MANAGER** 运营主管 | 全部经营功能，可看租户内所有店铺 | 不能改用户角色 |
| **AGENT** 客服 | 回消息、看会话与商品、申请转人工 | **看不到底价**、不能改商品、不能发货 |
| **VIEWER** 只读 | 看报表 | 任何写操作 |

### 两个容易踩的权限点

**1. 客服看不到底价，这是故意的。**

底价是店铺最核心的商业机密，客服流动性大。所以底价是在**服务端**就从返回数据里摘掉的，不是前端不显示 —— 抓包也看不到。

**2. 店铺范围必须显式指定。**

除 MANAGER 外，其他角色的每个请求都要带可访问店铺范围。系统**不会**在你没指定时默认"全都能看" —— 那是最典型的越权来源。

> 如果你发现自己看不到某个店，先确认账号是否被分配了该店的访问范围。

## 三、总览页（Dashboard）

每天开工先看这一页。

### 四个数字卡片

| 指标 | 含义 | 健康值 |
|---|---|---|
| **健康分** | 六项指标加权总分 | ≥ 80 良好；< 60 需处理 |
| **今日咨询** | 今天处理的消息数 | 结合店铺单量看 |
| **FAQ 命中率** | 无需调用大模型就直接答上的比例 | **≥ 60%** 说明配置得好 |
| **待处理工单** | 需要人工介入的累积量 | 越少越好，P0 必须清零 |

### 健康分怎么算的

六个指标加权：

1. FAQ 命中率
2. AI 处理占比
3. 转人工率
4. **P0 未处理工单数**
5. 重复消息率
6. 缺货商品数

下方会列出具体问题，例如「FAQ 命中率 当前 0.0，目标 >= 0.6」—— 直接照着修即可。

### 重复消息率

正常应接近 **0**。这是**免费的断线探测器**：

- 突然升高 → 平台连接在重试，或消息被重复推送
- **后者可能引发重复发货**，需要立即检查

### 店铺矩阵

列出每个店铺的负责人、在线状态、自动回复/自动发货开关。

## 四、商品与库存页（Products）

### 库存与自动下架

按商品列出：

| 列 | 说明 |
|---|---|
| **状态** | `OK` 正常 / `LOW` 偏低 / `OUT` 已空 |
| **可用 / 阈值** | 当前卡密数 / 告警线 |
| **日均消耗** | 根据历史发货推算 |
| **预计可支撑** | 还能卖几天（`cover_days`）|
| **优先级** | 告警等级 |
| **自动下架** | 是否已因缺货自动暂停 |

**缺货逻辑**：当可用卡密降到阈值以下，系统可以自动下架该商品，避免买家付款后发不出货。这是保护店铺评分的关键机制 —— 卖出去发不了比没卖出去更糟。

### 商品诊断

点「运行诊断」，填入商品的**咨询/议价/成交/库存/上架天数**，系统给出结论：

| 结论 | 含义 | 建议方向 |
|---|---|---|
| 曝光足但成交少 | 有人看没人买 | 检查价格或详情 |
| **议价多但成交少** | 砍价的多，成交的少 | 底价可能高于买家心理价位，或让得太慢 |
| 库存积压 | 长时间卖不动 | 考虑降价或换品 |
| 正常 | 转化健康 | 维持 |

示例：某商品"60% 的咨询在砍价，但成交率仅 2%"→ 建议检查底价是否设得过高。

## 五、捡漏监控页（Monitor）

用于按条件筛选值得采购的二手/低价商品。

### 操作步骤

1. 选择店铺
2. 填监控参数：

| 参数 | 说明 | 默认 |
|---|---|---|
| **关键词** | 标题必须包含 | 必填 |
| **市场价** | 用于算折扣 | 必填 |
| **价格区间** | 只看这个价位 | 不限 |
| **最低想要人数** | 过滤冷门 | 不限 |
| **多模态折扣阈值** | 折扣超过此值才触发图片鉴真 | 0.15（即 85 折）|
| **每日鉴真预算** | 控制成本 | 50 次 |

3. 填候选商品（或点「填入示例」）
4. 点「运行筛选」

### 关键词怎么匹配

**商品标题必须包含关键词才会通过**。填「显卡」时，标题里没有"显卡"两个字的商品会被直接淘汰，理由显示为 `KEYWORD_MISS`。

> 这是第一道过滤，也是最容易让人困惑的地方 —— 筛选结果为空时先检查标题用词。

### 三级过滤链（为什么要这样设计）

```
① 关键词 + 价格区间 + 想要人数     ← 零成本，过滤掉绝大部分
        ↓ 通过
② 折扣是否够深                     ← 零成本计算
        ↓ 折扣够深
③ 多模态看图鉴真                   ← 花钱，只对最可疑的少数调用
```

**第 ③ 级是成本大头**（约 ¥0.02/次），所以只对「折扣够深 + 标题可能有坑」的候选调用。

### 关于「跳过鉴真」

未配置多模态模型（`QWEN_API_KEY`）时，需要鉴真的候选会**直接放行而不是丢弃**：

- 好处：不会因为没配模型就漏掉好货
- 风险：无法识别标题淡化的瑕疵

结果里的 `vision_skipped` 就是被跳过的数量。跳过很多时，建议配上模型再跑。

### 结果怎么看

| 字段 | 含义 |
|---|---|
| `accepted` | 通过的商品 ID |
| `rejected` | 淘汰的，含**原因**和**说明** |
| `vision_calls` / `vision_cost` | 实际调用了多少次鉴真、花了多少钱 |
| `vision_skipped` | 因预算或阈值被跳过 |
| `budget_exhausted` | 预算是否已用尽 |

> **预算用尽后是降级放行**，不是丢弃候选 —— 宁可多给你几个也不要漏掉。

## 六、审计日志页（Audit）

**查"谁改了什么"的地方。**

### 用法

- 可按动作类型筛选，如 `MIN_PRICE_UPDATE`
- 列表显示：时间、操作人、动作、对象、变更

### 变更记录长什么样

只记**实际变化的字段**，且敏感值会打码：

```
字段: min_price
变更: 99.0 → 95.0
标记: critical（关键字段）
```

### 哪些操作会被记录

| 动作 | 说明 |
|---|---|
| `MIN_PRICE_UPDATE` | 改底价 —— **关键操作，会触发告警** |
| `PRODUCT_UPDATE` | 改商品其他字段 |

改底价会返回 `needs_alert: true`，是重点审查对象。

## 八、AI 客服是怎么处理消息的

买家发来一条消息，系统按固定顺序处理。**顺序很重要**，理解它能解释大部分"为什么 AI 这样回"。

```
收到消息
   │
   ├─① 幂等去重：重复消息直接丢弃（不花钱）
   │
   ├─② 人工接管中？→ AI 闭嘴，不发言
   │
   ├─③ 站外引流检测 → 命中则拦截 + 自动兜底话术
   │
   ├─④ FAQ 匹配（相似度 ≥ 0.6）→ 命中则直接回答，零 LLM 成本
   │
   ├─⑤ 调用大模型 → 拿到回复和报价
   │       └─ 若给了报价 → 服务端硬校验（见第九节）
   │
   └─⑥ 转人工判定 → 达到阈值则开工单
```

### 五种返回动作

| `action` | 含义 | 买家看到什么 |
|---|---|---|
| `FAQ_HIT` | FAQ 命中 | 预设答案 |
| `AI_REPLY` | AI 回复 | 模型生成的回复 |
| `DEFLECT` | 站外引流被拦 | 自动兜底话术 |
| `HANDOFF` | 转人工 | "正在为您转接人工客服" |
| `DROP_DUPLICATE` | 重复消息 | 无（静默丢弃）|

### FAQ 命中率是成本的关键

FAQ 命中不调用大模型，**零成本**。命中率 ≥ 60% 时文本成本可忽略不计。

**提升办法**：把高频问题（多久发货、怎么激活、能不能退）都配成 FAQ。

## 九、议价规则与底价保护

这是系统最值得理解的部分，因为它直接关系到**会不会亏钱**。

### 议价阶梯怎么算

商品配置里有个「议价阶梯」，例如 `[0.05, 0.12, 0.23]`，表示每轮最大让步比例：

| 轮次 | 最低可报价 | 以挂牌 128 为例 |
|---|---|---|
| 第 1 轮 | 挂牌 × 0.95 | 121.6 |
| 第 2 轮 | 挂牌 × 0.88 | 112.6 |
| 第 3 轮 | 挂牌 × 0.77 | 98.6 |

**但无论阶梯怎么走，下限都会被底价兜住。**

若底价是 99，第 3 轮算出的 98.6 会被抬回 **99** —— **阶梯永远不允许穿透底价**。

### 三道防线

```
第一道：底价存在数据库，服务端校验才有权读
第二道：AI 的报价必须落在本轮合法区间内，否则整条回复作废
第三道：拿不到商品信息时，一律不允许报价
```

### 报价越界会怎样

**不会**把价格"夹"回区间内，而是**整条回复换成兜底话术**：

> "这个价格实在做不了哈，已经是我能给的最低了，您看可以的话就直接拍～"

**为什么要整个作废而不是改价格？**
因为回复文本里通常已经写明了金额。只改价格会造成"文本说 90、实际报 95"的自相矛盾 —— 买家截图投诉时你没法解释。这种不一致比直接拒绝更危险。

### 为什么拿不到商品信息就不报价

如果平台推送的商品 ID 与本地登记不一致、商品被删、或消息不在商品上下文中，系统**无法判断报价是否合法**，此时会：

- 改用兜底话术
- 不报任何价格
- 标注 `缺少商品上下文，无法校验报价`

> 这是一条关键保护。否则 AI 可能说出"¥10 可以给您"而底价是 99。

### 你会看到的字段

| 字段 | 含义 |
|---|---|
| `intent` | 意图，`BARGAIN` = 议价 |
| `offered_price` | 实际报给买家的价格（**已通过校验**）|
| `note` | 说明，如"AI 报价越界，已丢弃报价并改用兜底话术" |

## 十、转人工机制

### 两种触发方式

**1. 立即转人工**（不看分数）

| 情况 | 关键词示例 |
|---|---|
| 买家明确要求 | 转人工、人工客服、找店长、叫你们主管 |
| 投诉举报 | 投诉、举报、差评、曝光、报警、12315 |

这两种再让 AI 多说一句都是错的。

**2. 按信号累加分**

| 信号 | 权重 |
|---|---|
| 站外引流被拦 | 50 |
| AI 置信度低 | 40 |
| 反复未解决 | 35 |
| 负面情绪 | 30 |
| 议价僵持 | 25 |

- 总分 **≥ 60** → 转人工
- 总分 **≥ 80** → **P0 加急**

### 工单优先级与时限

| 优先级 | 处理时限 |
|---|---|
| **P0** | 5 分钟 |
| **P1** | 15 分钟 |

超过时限的 70% 会标记为「即将超时」。

### 转人工时 AI 会做什么

- 给买家发固定话术：「好的，正在为您转接人工客服，请稍等片刻～」
- 同时**保留 AI 已生成的草稿**给人工参考（字段 `draft_reply`）
- 工单进入队列，可在总览页看到待处理数

### 拦截优先原则

如果同时命中站外引流和转人工，**两件事都做**：话术照发（止损更紧急），同时开工单。

## 十一、退款决策规则

系统的判定顺序是刻意设计的：从"确定该退"到"确定不该退"，中间落人工。

### 判定顺序

```
1. 订单尚未发货          → 自动同意（零损失，与理由无关）
2. 理由无法识别          → 转人工
3. 重复支付              → 自动同意
4. 卖家责任（卡密无效/发错货）→ 自动同意 + 补发或补偿
5. 买家责任 + 卡密已查看  → 自动拒绝
6. 其他情况              → 转人工复核
```

### 退款原因分类

| 原因码 | 归属 | 处理 |
|---|---|---|
| `NOT_DELIVERED` | — | 未发货必退 |
| `CARD_INVALID` | **卖家责任** | 自动同意，需举证 |
| `WRONG_ITEM` | **卖家责任** | 自动同意，需举证 |
| `CARD_ALREADY_USED` | **买家责任** | 卡密已查看则自动拒绝 |
| `NO_LONGER_NEEDED` | **买家责任** | 卡密已查看则自动拒绝 |
| `DUPLICATE_PURCHASE` | — | 自动同意 |
| `OTHER` | — | 转人工 |

### 为什么"未发货"放在第一条

未发货是**客观事实**，与买家说了什么理由无关。

不该因为理由文本没被识别，就把一笔零损失的退款压给人工去点按钮。

### 高风险买家不会自动拒

即使属于买家责任，如果买家风险分 ≥ 60，系统仍会**转人工复核**而不是自动拒绝 —— 避免误伤，也让决策留痕。

风险分由这些累加：退款频率、站外引流次数、投诉次数。

## 十二、常见场景速查

### 场景：买家砍价砍得太狠

**系统行为**：AI 报价超出本轮合法区间 → 整条回复替换为兜底话术，`offered_price` 为 `null`。

**你要做什么**：如果觉得 AI 让得太慢导致丢单，去商品配置里调**议价阶梯**；如果觉得让得太快，检查**底价**是否设低了。

### 场景：买家要求加微信

**系统行为**：`action: DEFLECT`，自动发送兜底话术，同时可能转人工。

**你要做什么**：无需干预。这是合规必须的拦截，话术已自动发出。

### 场景：买家说"我要投诉"

**系统行为**：立即转人工，开 **P0 工单**（5 分钟时限）。

**你要做什么**：立刻上总览页看工单，5 分钟内响应。AI 已经闭嘴了。

### 场景：某商品卡密快用完

**系统行为**：「商品与库存」页显示 `LOW`，接近阈值时可自动下架。

**你要做什么**：尽快补卡密。若已自动下架，补完后需手动重新上架。

### 场景：买家申请退款，卡密已经给过了

**系统行为**：
- 若是"卡密已用/不想要" → `AUTO_REJECT`（30 分钟时限）
- 若是"卡密无效/发错货" → `AUTO_APPROVE` + 需要举证

**你要做什么**：留意 `REVIEW` 状态的，那是需要你判断的。

### 场景：健康分突然掉下来

**排查顺序**：
1. 看总览页列出的**具体问题**（系统会直接写出来）
2. 检查 **P0 工单**是否积压
3. 检查**重复消息率**是否异常（可能平台在重试）
4. 检查**缺货商品**数

### 场景：AI 回复说"没配大模型"

**系统行为**：`note: 未配置大模型客户端`，FAQ 和规则仍正常工作。

**你要做什么**：配置 `DEEPSEEK_API_KEY`（找运维）。这不影响 FAQ 与拦截功能。

## 十三、常见疑问

**Q：为什么客服账号看不到商品底价？**
底价是核心商业机密，客服流动性大。底价在服务端就被摘掉了，不是前端隐藏，抓包也看不到。

**Q：为什么拣漏筛选结果为空？**
先检查**商品标题是否包含关键词**。第一道过滤就是关键词匹配，标题里没有对应词会直接淘汰（显示 `KEYWORD_MISS`）。

**Q：AI 报价被系统拒绝了好几次，会不会丢单？**
拒绝的是"越界报价"，会换成兜底话术继续沟通，不会中断会话。如果频繁发生，说明**议价阶梯设得太紧**，建议放宽。

**Q：转人工后 AI 还会回复吗？**
不会。会话一旦进入人工接管状态，AI 会保持沉默（返回 `SILENT`），避免和客服抢话。

**Q：同一条消息被处理了两次怎么办？**
正常情况下系统有幂等去重。如果确实重复了，检查是否**未配置 Redis 且多实例部署** —— 这种情况下去重只在单进程内有效。

**Q：重复消息率突然升高说明什么？**
通常是平台连接在重试，或消息被重复推送。后者**可能引发重复发货**，需要立即检查。

**Q：多模态鉴真是每次都调用吗？**
不是。只有折扣够深（默认超过 15%）的候选才会触发，且有每日预算（默认 50 次）。预算用尽后是**降级放行**而非丢弃候选。

**Q：为什么改底价会触发告警？**
底价直接决定议价下限，是能造成实际亏损的字段，所以单独列为关键操作并记入审计。

**Q：健康分多少算正常？**
≥ 80 良好，60~80 需关注，< 60 需处理。系统会直接列出扣分项。
